# U3 - boot recovery covers transactions and events; undo a restore in two places (owner decisions)

**Recovery panel (plain DOM, `src/events/import-export.js`; logic in `src/state/backup.js`)**
- Export now writes a full v2 backup bundle (settings, transactions, events, and any other registered part such as scenarios), the same format as the normal backup. `collectRecoveryBundle` reads the saved settings text defensively and every part on its own with a 10 second limit. A part that cannot be read (error, not a list, or a hang) is left out and named plainly in the message ("these could not be read, so they are not in it: your transactions and your events"). The file is still saved. If the saved settings text is not valid, the raw text is carried in the file as `unreadableSettingsText` and the settings are named as unreadable. Only when nothing at all can be read does it say there is nothing to export.
- Import uses `restoreFromRecovery`, which runs the normal `commitBackup` (rows copy in the safety database, settings copy, rows swapped, rollback of every part and the settings on any failure, a failed main save counts as a failure). The settings are then written to the main save and the page reloads. If the saved text is not JSON, it is set aside as `ft-corrupt-save-*`, removed while the restore runs (the copy step reads it) and put back if the restore fails.
- Reset is unchanged: it clears the saved settings after keeping a copy, and does not touch transactions or events (clearing those needs a ruling).
- Known limit: if the current transactions or events cannot be read, no safety copy can be made, so a recovery import is refused with the existing "could not read your current transactions" message. A file with no settings (exported when the settings were unreadable) cannot be imported (it has no `financeData`).

**Undo a restore**
- After a successful restore an Undo toast (the existing toast-with-Undo, 12 seconds) shows the "Backup restored" message. Undo runs `undoLastRestore` (settings plus every part). Letting it expire leaves the restore alone.
- Settings, Your data: a row "Put back what was here before the restore (from 22 Nov, 12:09 am)" sits after "Restore from a backup". It is shown only while a full copy exists (settings copy marked with rows AND a matching rows copy). It asks first with the app's confirm dialog ("Put back your earlier data?"). New pure helper `src/ui/restore-copy-row.js` adds it; `settings-screen.js` looks for the copy on open and on the new `ledger:restore-copy-changed` event.
- How long the copy stays: until the next restore replaces it (one slot), until Erase all removes the rows copy (an erase keeps a settings-only copy, which shows no row), or until an undo spends it. A successful undo removes both halves of the copy (`undoLastRestore` now ends with `discardRestoreCopy`; option `spend: false` keeps it). A failed undo keeps it. It is not cleared by a page reload.
- Strings added in `src/i18n/en-d.js` (`d.recovery.*`, `d.settings.undoRestore*`, `d.undo.*`), Australian English. One existing string changed: `d.recovery.nothing` now also covers "none of it could be read".

**Tests added:** `src/state/recovery-undo.test-cases.js`, groups `recovery-undo` (U3.1 to U3.8, 44 assertions, pure) and `recovery-undo-browser` (U3.9, the real toast and its Undo button). No existing test changed. Real-browser check with synthetic data at 390 and 1440, light and dark (40 checks): forced boot failure shows the panel, export holds 5 transactions and 1 event, broken IndexedDB gives the partial message, restore shows the Undo toast, toast Undo and the Settings row both put the rows back, the row is hidden before a restore and after an undo.

**Left for later:** Reset does not clear transactions or events (needs a ruling). A recovery import cannot proceed when the current rows are unreadable. The toast pill is narrow at 390 (existing toast style, not changed here).
