# S9 - restore safety copy moved to IndexedDB; Erase all keeps no rows copy; a failed save fails the restore (G6W15-1, G6W15-2, G6W15-6)

**What changed**
- New `src/state/safety-db.js`: a separate small database `ledger-safety-db` (version 1, one `copy` store, one record) holds the rows copy of every registered part. `ledger-db` keeps version 2, so open tabs are not asked to upgrade. If the copy cannot be stored, the restore is refused as before (`cantKeepCopy`).
- `commitBackup` (src/state/backup.js): `takeSafetyCopy` writes the rows record `{id, timestamp, parts}` to the safety database, then the settings copy (`ft-pre-restore-backup`) carrying the same `copyId`, `copyTimestamp` and `hasRows`. A half copy (settings write failed) is removed. `commitImport` no longer rewrites the settings copy for a backup restore (`copyTaken`).
- `undoLastRestore` refuses a pair that does not match (`copyMismatch`): wrong or missing id (for example the recovery panel's `keepCopy` wrote only the settings), or a missing rows copy when the settings copy says it has rows.
- Erase all (`commitErase`, `keepRowsCopy: false`): only the settings copy is kept (as the dialog says), no rows copy is written, and any earlier rows copy is deleted from the safety database and the old `ft-pre-restore-parts` key on success. The erase dialog now also says transactions and events are not kept (`d.erase.body`).
- The retired localStorage key `ft-pre-restore-parts` is removed on every load (`removeLegacyPartsCopy`, called from `loadData`).
- A failed main save counts as a failed restore: `AutoSave.forceSave`/`performSave` now return true or false; `commitImport` treats `save() === false` as a failure and runs the existing rollback (rows, settings, redraw) with the existing message. The two callers (`import-export.js`, `settings-events.js`) now return the result of `forceSave()`.
- S5 guard: `ledger-safety-db` goes to a scratch name (`ledger-test-scratch-safety-db`), is left out of the database-list check and is dropped at the end.

**Tests added:** S9.1 to S9.4 (settings group, pure: erase leaves no rows copy anywhere, same-id pair and mismatch refusal, a failed save rolls back for restore and erase, legacy key removed) and S9.5 (new browser group `safety-db`: a restore with 20,000 synthetic transactions keeps its copy in IndexedDB, undo brings all back, erase leaves no rows copy). Existing S8/D2 tests were adapted to the new copy location, none weakened. run-cases 2754 passed (was 2713); tests.html 3191 of 3191.

**Probe (erase-probe, built dist):** Erase all with 200, 8,000 and 20,000 rows: all succeed, 0 rows left, no rows copy in localStorage or the safety database, localStorage headroom 5,226,562 characters each time.
