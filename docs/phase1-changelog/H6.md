# H6 What If must work exactly like the app (equivalence suite and fixes)

Chilli's rule (2026-11-22): an edit in a scenario changes every dependent figure the way the same edit does in the real app; the only difference is that it runs on a copy. H5 showed the architecture (`resolveAt` on a copy, then the normal calculations) can still break. H6 proves the rule for every change kind and fixes what broke it.

## The suite (group `scenario-equivalence`, `src/ui/scenario-equivalence.test-cases.js`, 295 assertions)

For each change kind and op the UI can produce, on three households (the sample, a salaried source with payslip figures, and a source migrated from Self-employed then switched to Salary):

- Path A: `resolveAt(data, changes)`, then every figure What If shows through `buildResultSet` (cards, all numbers and Compare rows, the FI path and chart, FI years and number, goals, Explain lines).
- Path B: the same edit on a deep copy through the app's own save functions (`applyIncomeValues` with `sheetValuesFor`, `updatePlanItem`, `removePlanItem`, `setSplit`, `addGoal`, `updateGoal`, `removeGoal`, `applyAssumptions`, `newDebt` + `applyDebtValues`, `newIncomeSourceRow` + the Salary sheet), then the figures worked out the way the screens do: `netPerPayCents`, `getBuckets` (Plan), `planGoalsFromData` and `goalsModel`, `fiSummary(withPeople(data))` and `projectNetWorth` (Future), `calculateTotals`.
- Asserted equal: the figures, the buckets and goals, the Explain text, and the resolved data against the edited data (every field the app's save writes that the scenario did not shows as a named path).

Cases: income set and scale (rise, cut, new job swap, dated today), expense set, scale, group scale, set to nothing, remove, split set, goal add (one and several), set (cost, date), remove, incomeAdd, debtAdd, assumption set, scale, add, and one scenario with several kinds together. Before the fixes 84 of the 295 assertions failed; after, none.

## What broke it, and the fix (shared engine, not only What If)

| Divergence | Cause | Fix |
|---|---|---|
| Any change touching the essentials, a loan or an assumption moved only the later years of the net worth path, FI years and the nw rows | `fi.js` opened the plan (Mojo target, loans, HELP) from the unresolved data | `openingData()` in `fi.js`: projectNetWorth, yearsToFI and fiSummary open from the data with the changes active today applied |
| The FI Explain lines in What If showed the old spend, multiple, return, going-toward figures | `fiSummary` read its own lines from the unresolved data | same `openingData()` |
| Extra income gave no super and no withholding declaration (long-range path and FI years wrong) | the new row had none of the fields the Salary sheet writes on a first save | `fillNewSalarySource` in `income-rebase.js` (super 12 percent default now shared with the sheet, `basis`, withholding declaration) |
| A new loan did not change the net worth path | same opening-data cause | `openingData()` |
| A new goal did not rebalance its siblings' shares or set its order; a dropped goal did not move its saved money up | the scenario pushed or spliced the row | `applyOne` calls the app's `addGoal` and `removeGoal` |
| A split of 33.33 kept two decimals | the app's `setSplit` rounds to one | rounded the same way |

Not changed on purpose: nothing about take-home or the plan screens needed a fix beyond H5.

## Savings rate, which screen uses which (no change made)

| Screen | Function | Definition |
|---|---|---|
| Today, "Savings rate (planned)" (`today.js`, `savingsRateFigure`) | `calculateTotals().savingsRate` (`calculations.js` 151) | (net minus planned expenses) over net; moves with pay |
| Today, "Savings rate (actual)" | transactions for the last full pay cycle | income minus spending over income |
| Future, FI card (`future/view.js`) | `fiSummary().savingsRate` = `savingsRatePlanned` (`fi.js`) | save buckets over net pay; does not move with pay |
| What If, cards, Show all numbers, Compare, Explain (`results.js`) | `savingsRatePlanned` | same as Future |
| Snapshots and milestones (`snapshots.js`, `milestones.js`) | `calculateTotals().savingsRate` | same as Today planned |

So What If's "Savings rate" matches the Future card and not the Today figure; the three labels are the same words. On the plain sample the two definitions agree (29 and 29.1) by construction; on the migrated household they are 29 and 24.7. A test pins that What If equals the Future card. Which one is "the" savings rate is a design question for Chilli.

## Needs a design call (not built)

1. A pay change on a Self-employed or Variable source is silently inert (take-home and net worth unchanged, no message). The app has no gross edit for those types, so there is no real edit to match. Options: scale their net and tax per pay, or refuse the change.
2. A loan with a start date in the future shows in the Debts row but never enters the net worth path (the path opens from today). Same for any dated change to an opening balance. Needs a rule for when a loan's money arrives.
3. `oneOff` and `goalFund` are virtual: no figure reads `scenarioOneOffs`, and a ticked balance has no real equivalent. No starter produces a one-off or an assumption change yet; they are tested at engine level only.
4. Hourly-layout sources: a What If pay change sets the gross and leaves the stale hourly rate and hours (the real sheet derives gross from them). Figures match; Make this real pre-fills a rate.
5. Savings rate definition (above).
