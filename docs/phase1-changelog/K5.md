# K5 - the flaky E10.1 test

## Cause
E10.1 (tax-pot comparison, `bucket-method.test-cases.js`) called `taxProvisionModel` four times without a `now`, so each call read its own `new Date()`. The model's `fyElapsedFraction` uses `now.getTime()` to the millisecond, and the test deep-compares two results (`loose` against `behind`). When the millisecond ticked over between those two calls, `prov.elapsed` differed in the 8th digit and the comparison failed. A second, rarer hazard: the event date came from a separate `new Date()`, so at midnight or the 30 Jun / 1 Jul FY boundary the event could fall outside the FY.

## Repro
Two calls with `now` 1 ms apart: `elapsed` 0.39406393943632484 against 0.3940639394680346, so the results are not equal.

## Fix
The test pins one clock (`new Date(TODAY + 'T12:00:00')`, TODAY = 2026-11-21) and passes it to every call; the event date is `TODAY`. No assertion weakened. Production code unchanged (it already takes `now`).

## Other tests at risk (not changed)
- `future.test-cases.js` F6.7: `futureModel(d, { today })` leaves `opts.now` unset, so the tax and HELP cards read the real clock. Not flaky within a run, but it will change behaviour when the real FY rolls past the sample's events. Fix would be passing `now` in `futureModel` options (a model change, listed only).
- `csv.test-cases.js` lines ~294-298, ~357-360: wall-clock speed asserts (under 500 ms, under 1500 ms); can fail on a loaded machine (several agents in parallel).
- `scenario.test-cases.js` and `smile-review.test-cases.js`: use `new Date(fixed)`, safe.
